# R9.2 四设备验收操作

用同一候选版在两台 Mac、两部 iPhone 上跑一遍。甲用 Mac A 和 iPhone A，乙用 Mac B 和 iPhone B。每轮使用独立测试目录、测试成员和合成数据。先跑受控链路，再用候选版配置的真实模型跑语义。按用例编号填写 [验收表](../../outputs/r9-2-four-device-review/验收表.md)。

## 构建与同机预跑

在候选版的测试 worktree 根目录运行。使用 `host/.bun-version` 指定的 Bun，先按项目 README 安装依赖。以下组合用例会自行创建临时数据库、身份和监听端口。

```sh
sh tools/check_all.sh
(
  cd host
  bun --no-env-file test test/integrated-runtime.test.ts test/peer-gateway.test.ts \
    test/group-sends.test.ts test/publication-lease.test.ts test/peer-behavior.test.ts \
    test/typed-peer-runtime.test.ts test/relay.test.ts \
    test/file-blobs.test.ts test/world.test.ts test/binary.test.ts
  LC_ALL=C CATTT_TEST_PG=1 bun --no-env-file test test/import-pg.test.ts
)
```

PG 用例需要 `initdb`、`pg_ctl`、`psql`，会自建临时集群。R8.18 的 `files-gateway.test.ts` 还会绑定默认 peer 端口 8790，适合独占本机时单跑；双宿主附件组合已从临时端口覆盖。macOS 成品走候选树的 Bun 打包入口 `bash desktop/macos/scripts/build-bun-app.sh`。将 `CATTT_BUN_APP` 指到实际候选 App，再运行 `python3 desktop/macos/scripts/smoke-bun-host.py` 和 `python3 desktop/macos/scripts/smoke-bun-backup.py`。前者的 `--gui` 仅在获准使用的独立桌面会话运行。原 `smoke-host.sh` 使用 v1 的固定端口、Node 和 PG，适用于旧成品。iOS 用 `Maomao` scheme 跑 `MaomaoV2Tests`，使用分配给本轮的模拟器。 [Mac 构建说明](../../desktop/macos/README.md) · [iOS 构建说明](../../ios/README.md)

## 四台设备操作顺序

下文的手机 API 从各成员自己的 Mac 走 HTTPS，核对 CA 指纹并验证主机名。管理接口只从该 Mac 的回环访问。设备令牌、管理令牌、配对码、邀请链接和含私钥的备份不进入证据文件。

1. **装包与导入（01、02、12）。** 记录 macOS App/DMG、iOS 安装包或归档及实际嵌入的 Bun 二进制。Mac 记录开发签名或正式签名，正式分发件保留 `codesign --verify --deep --strict`、`xcrun stapler validate`、`spctl --assess --type execute` 的输出及首次打开证据。两部 iPhone 从指定工件安装或升级，记录实际打开的版本。在 iPhone A 升级前留四条样本，分别是已同步到旧宿主、仅本机模拟、待上传和已撤回。另用旧 PG 的只读测试快照，在 Mac A 的空目录运行成品内的 `cattt-host import-pg --target-dir <新宿主目录>`，连接从 `CATTT_IMPORT_PG_URL` 注入。同一快照重跑先取 `imported` 再取 `verified`，逐表核对数量、关键字段哈希及各归档原因。启动 A 后抽查 Han 的旧聊天、召回、日记许可、托付、约定、信箱。记录启动、B 安装首轮业务快照前后的旧任务、通知、信件计数，验证历史无新增执行。旧版和旧 PG 备份保留。
2. **结对与邀请（03）。** 先在两台 Mac 的「家庭与手机」完成 peer 指纹双向确认，让空的 B 加入并拉到首成员和群聊。A 为 Han 签发 v2 配对 QR，iPhone A 扫码并核对指纹。B 签发家庭邀请，iPhone B 从链接打开或在「我的 → 使用家庭邀请链接」粘贴，核对 B 指纹、填名并确认。用两部手机核对本人、归属 Mac、同一家庭及同一群聊。重用已消费链接应失败。拿有原配对和草稿的测试手机尝试无效邀请，应能继续使用原身份与草稿。用双方设备凭证交叉读取对方单聊，列表仅有本人单聊和群聊，详情/历史按契约拒绝。两台 Mac 的业务副本仍会复制单聊。
3. **并发、断网和交接（04、05、06）。** 双方约同一时刻各发一条「团子，看看 A/B 的群聊消息」，再同时发一条本人单聊标记。各自的 Mac 打开群聊观察同步和署名。待同步后从 `GET /v2/conversations/:id/messages` 核对四条输入的会话、作者和 ID。接着隔断两 Mac 间的 peer 通信，先保留手机到各自 Mac 的连接以验证单聊仍响应。超过候选版公布的租约窗口后让 A 休眠，B 继续发群聊。在 A 恢复联网前后采集两端 `GET /host/publication-lease`，记录时间、持有者、状态、代次及发布宿主。历史补齐后从旧持有方发起交接，API 为 `POST /host/peers/:id/lease`，传唯一的 `request_id` 和当前 `expected_epoch`。确认新代 ready，再逐个核对旧代迟到任务与新代输出。
4. **复核同键和对端收据（06）。** 在失联期间从非发布方带固定 `client_message_id` 向 `POST /v2/conversations/:id/messages` 发送。收到 202 时保存 `receipt_url`，对端离线时反复查询应保持待送达。断开手机网络、杀掉并重开测试 App，再接通。用同一键和正文重试，比较原收据与最终消息 ID。另用同键改正文，预期 409。同机预跑的 `group-sends` 用例会丢弃目标已提交的 HTTP 回执，预期查询仍为 202，直到对端真的回传原收据。实体仅能确认此故障时，才填写该子项的实体结果。
5. **来源许可和转告（07、08、09）。** 在安静时段之外，用同一发送者当地日提交三条普通转告、第四条普通转告、一条紧急转告，以及一条明确说「别告诉 TA」的请求。用「帮我转告：带伞」或「帮我紧急转告：请改走北门」作为输入。若候选界面尚无对应入口，先记下原话 ID 和修订，再通过 `POST /v2/relays` 提交。核对 B 单聊的 A 署名、目标 Inbox 收据与实际单聊消息，次日再核对普通额度。用有可用来源的合成记忆和获准读取日记，先在 B 确认可见/可召回，在 A 用「立即备份」保存这一检查点。随后断开 peer，在 A 撤回原话或收紧日记许可。B 重连后用撤回前的 `/v2/changes` 游标查询，并在冷窗口追问。核对墓碑、许可、等待中的转告和迟到的旧证据。真实模型的对照语料见下方。
6. **附件、恢复和手机升级（10、11、12）。** 用同一合成附件上传一半后断线。用 `GET /v2/files/uploads/:id` 检查 A 的偏移，检查 B 尚不可下载。重启或恢复网络后从已确认偏移续传，记录原件的 `shasum -a 256`、`POST /v2/files/uploads/:id/complete` 响应、B 从 `/v2/files/:id/content` 下载的文件哈希。也跑错误哈希与来源撤回。Mac A 用「从备份恢复」选择第 5 步的备份，B 保留最新业务状态。观察旧许可、已完成事项、租约与同键收据，记录恢复前后同步世代及两部手机重拉。iPhone A 配对 v2 后重开 App，核对第 1 步的本机模拟条目仍归原空间、允许迁移的条目一次入库，撤回仍然有效。恢复期间从手机各留一条离线文字和附件，重连后核对每个原键仅投递一次。

## 真实模型复跑

在 `host/` 按候选树 README 的「模型实评复跑」运行 `test/memory-eval/r4-real.ts` 和 `test/model-eval/worker-real.ts`，只给隔离进程注入经授权的模型配置。记录实际调用的 provider、模型 ID、槽位、权重版本（本机）、思考模式、账本及两份脚本的退出码。将两位成员相反的同类偏好（甲喜欢热美式，乙只喝无糖豆浆）、群聊提到对方、代词含混、团子的旧提议、撤回前后各重复一轮。逐条比较成员、值、原话和修订，另评冷窗口最终回复。明确未知或待确认是反例的通过条件，不能计成已确认记忆。补测猫日记按家庭自然日生成一次，换宿主和撤回后检查许可及出处。

每一步把实际结果和工件名填入对应编号。复现失败时保留完成前后的 HTTP 状态、消息 ID、修订与时间，再从同一候选和同一测试数据重跑。
