## 1. 要交付的体验

团子仍然是你在聊天里认识的那只猫，只是它不再只在你开口的那几秒里存在：

- **约好的事。**你说“明晚问我面试怎么样”，团子确认一次；到了明晚，它在同一段聊天里问你，院子的信箱旗子竖起来。你可以在“我的”里看到、改时间或取消。
- **托团子的事。**你说“帮我想想周末去哪，想好了告诉我”，团子说“好，我想想”就安静下来；后台用更强的思考把事办完，结果作为一封信放进信箱，并在聊天里说一句。办不成就如实说办不成，不硬凑。
- **团子自己的日子。**每天一篇猫日记，由服务端按你所在的日期写，只依据真实发生过的事；你没来的日子，它也写自己的日常，不编造和你的共同经历。
- **它知道什么时候别开口。**安静时段不打扰，同一天不反复找你，你说“不要再提”或关掉主动开口，它就停。

产出一律先落进聊天或信箱，推送只是“团子往信箱里放了东西”的提醒渠道。

## 2. 不做

- 通用办事助理：联网检索、读写外部文档、执行代码、连接日历邮件。见评审点 1。
- 任何形式的打卡、连续天数、等级、清单式待办界面；界面上不出现“任务”这个词，用“约好的事”“托团子的事”。
- 每个用户常驻一个大模型会话；后台持续模拟院子。
- 多猫、语音、网页接聊天。
- 本方案不处理消息删除契约（09-27 方案第二段第 5 条另评）。

## 3. 参考：DeepSeek Super-agent 取什么、不取什么

依据：开源原型 [deepseek-ai/dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype) 的 `docs/000`～`007` 与 `prompts/`（MIT，研究原型，非正式产品）；文章《Super-agent 设计探索》原文在微信公众号，这里只依据仓库文档与[第一财经转述](https://m.jiemian.com/article/15278252.html)。

**取：**

| 它的做法 | 在本方案里 |
|---|---|
| 注意力是第一约束：只在被要求或写好的规则允许时行动；只在有结果、要决定、做不完时开口；开工时确认一次 | 第 5.7 节注意力预算、第 5.5 节执行者只经报告开口 |
| 事件流水线：来源 → 事件 → 线程 → 评估（确定性准入 + 模型研判）→ 决定 → 工单（带授权）→ 派工 → 出口 | 第 5.1 节领域概念 |
| 已有工单的线程上，人追加的话直达工单，不再评估 | 聊天里说“改成后天”，直接交给那件约好的事 |
| “等待”属于来源，评估从不等待；定时做成会自己再检查的来源 | 时钟来源（第 5.3 节），因此不引入工作流引擎 |
| 主动能力 `off / observe / auto`，默认 `observe` 只记录“本来会接” | 第 5.6 节主动规则档位 |
| 决定之后的外部动作先存后做、幂等键、退避重试；出口按序发送；每种状态一个写者；核心不做 I/O | 第 5.4 节出口、第 6 节数据 |
| 执行者报告状态 `progress / waiting / ready / blocked / failed / dropped`；`dropped` 安静结束 | 第 5.5 节 |

**不取：**

| 它的做法 | 原因 | 本方案的替代 |
|---|---|---|
| 常驻的主会话（Router）累积上下文 | 每个用户一个常驻会话，成本随用户数线性增长且上下文膨胀 | 便宜模型、每次唤醒只读一张固定大小的快照、用完即弃（第 5.2 节） |
| 运行在 DeepSeek Harness 里，单 SQLite 文件、单团队、以操作者账号满权限执行 | Harness 在 npm 上仍是 0.2.x alpha/rc；不支持多租户；消费产品不能满权限执行 | Node + Postgres，每猫串行，工具白名单 |
| 规则由团队写、人工逐条审 `observe` 记录 | 消费产品里逐条看等于读用户私聊 | 规则由产品方写并版本化；用户许可另存；`observe` 期只看聚合指标，原文只在内测用户明确同意时看 |
| 每件工单一个工作目录与 shell | 本方案范围不需要执行环境 | 执行者只有 API 型工具 |

## 5. 架构

```
iOS（SwiftUI + WKWebView 3D）                         ▲ APNs（第五段）
   │ 聊天 POST /v1/messages（SSE）      │ /v1/world/events 前台提示 inbox
   ▼                                    │
API 进程 ──── 快速通道：团子回话（兼任用户消息的 Router，可调用约定/托付工具）
   │  写事件                                       │ 经出口发布
   ▼                                               ▼
PG（唯一真相）：triggers · tickets · runs · run_steps · outbox · 业务表
   ▲ 时钟来源（每 30 秒扫到期）        │ pg-boss 投递
   │                                   ▼
Worker 进程 ── 事件 Router（便宜模型，第二道研判）→ 决定
            └─ 执行者（更强思考）→ 报告 → 出口 → 聊天消息 / 信箱 / 推送待发
```

### 5.1 领域概念

内部名称只在代码与文档里用，界面不出现。

| 概念 | 代码名 | 规则 |
|---|---|---|
| 来源 | `source` | `chat`（用户消息）、`clock`（约定到期、跨日）、`world`（院子回执与水碗事件）、`diary`（主动给团子看的日记）。来源负责去重和“到点再看” |
| 事件 | `trigger` | 不可变；`(source, idempotency_key)` 唯一，同一事件只处理一次 |
| 线程 | 猫的唯一 `conversation` | 同一只猫同一时间只跑一个评估或一个快速通道回复（沿用现有对话锁）|
| 准入 | `gate()` | 确定性代码，第 5.6 节硬门；不调模型 |
| 研判 | `assess()` | 事件 Router 的模型判断，只决定“值不值得做、值不值得开口” |
| 决定 | `decision` | `accept`（开一件事）、`attach`（交给已有的事）、`ignore`、`silent`（值得记录但不开口），全部记原因 |
| 授权 | `mandate` | 不可变：`explicit`（用户亲口要求，附来源消息）或 `inferred`（命中某条主动规则，附规则 ID 与版本、依据原话）；用户取消即撤回 |
| 事项 | `ticket` | 用户看到的“约好的事 / 托团子的事 / 今天的日记”；只有决定能创建 |
| 执行 | `run` | 一件事的一次执行；步骤检查点存 `run_steps` |
| 出口 | `outbox` | 唯一能写用户可见内容的组件（第 5.4 节） |

### 5.2 两条路径与模型分工

**用户消息走快速通道，不先过 Router。**团子回话本身就是用户消息的 Router：在现有工具循环里增加约定与托付工具（第 6.3 节），边回话边决定要不要开一件事。只有工具返回保存成功的凭证，团子才能说“好，明晚问你”，与现有“记下了”同一套凭证规矩。聊天轮次继续在 API 进程内执行，以免首字前多一次队列轮询。

**其他事件走事件 Router。**时钟到点、跨日、院子事件、日记给团子看，先过准入，再由便宜模型研判。

| 角色 | 模型 | 思考 | 调用时机 | 预算 |
|---|---|---|---|---|
| 团子回话（兼用户消息 Router） | `deepseek-flash` | 关 | 每条用户消息 | 现状：4 步、6 次工具、45 秒 |
| 事件 Router | `deepseek-flash` | 关 | 事件通过准入后 | 1 次调用，输入快照 ≤ 3,000 token，输出固定结构，15 秒超时 |
| 执行者 | `deepseek-flash`；评审点 3 决定是否换更强模型 | 开 | 每件被接下的托付 | ≤ 20 步、≤ 10 分钟、累计输出 ≤ 8,000 token |
| 记忆提取、日记读取 | `deepseek-flash` | 关 | 现状不变 | 现状不变 |

新增 `ROUTER_MODEL / ROUTER_THINKING`、`WORKER_MODEL / WORKER_THINKING` 两组配置，默认值同上，在 `runtime/model.ts` 增加 `routerSlot()`、`workerSlot()`；成本账本 `model_calls.purpose` 增加 `route`、`errand`。

**事件 Router 的输入快照**（每次现建，不累积）：猫的性格段（与聊天同一前缀，命中缓存）→ 已开启的主动规则文本 → 准入结果 → 未结束事项清单（≤ 8 条，各 ≤ 80 字）→ 最近 6 条消息 → 本次事件卡片。

**事件 Router 的输出**，由代码复核后才生效：

```ts
{
  decision: 'accept' | 'attach' | 'ignore' | 'silent',
  ticket_id?: string,              // attach 时必填，必须是快照里的未结束事项
  rule_assessments: { rule_id: string, matched: boolean, reason: string }[], // 每条已开启规则恰好一条
  evidence: { message_id: string, quote: string }[], // inferred 接单必须引用真实原话
  goal?: string,                   // accept 时：这件事做完时应该是什么样，≤ 60 字
}
```

复核规则：`inferred` 的 `accept` 必须至少命中一条已开启规则且有证据，引用的消息必须属于本猫且 `context_allowed = true`；规则处于 `observe` 档时，`accept` 改记为 `ignore`（原因“本来会接”）；任何校验失败按 `ignore` 处理并记原因。

### 5.3 时钟来源

- 事项可带 `due_at`（UTC）与 `time_zone`；worker 每 30 秒扫 `due_at <= now()` 且未结束的事项，产生 `clock` 事件，幂等键 `clock:<ticket_id>:<due_at>`。
- 跨日：按每个用户的本地日期，在当地 00:05 后产生一次 `clock:day:<cat_id>:<yyyy-mm-dd>`，供第四段的猫日记使用。
- 改时间等于换 `due_at`，旧幂等键自然失效；取消即结束事项，已产生但未发布的事件在出口复核时被丢弃。

### 5.4 出口（唯一发布权）

所有用户可见产出只经 `publisher.publish(candidate)` 写出；`turns/run.ts` 与 `worker/diary.ts` 现有复核迁入这里，聊天快速通道的逐字发布也调用同一套复核函数。

发布前一律复核：

1. 归属：猫、用户、事项一致。
2. 授权仍有效：事项未取消；`inferred` 的规则仍开启且档位为 `auto`。
3. 来源仍可用：引用的消息 `context_allowed = true`，日记 `cat_allowed = true`。
4. 边界：与“不要再提”不重叠（复用 `memory/relevance.ts` 的 `boundaryOverlaps`）。
5. 记忆开关：`use_memories = false` 时不发布依赖记忆的产出。
6. 新鲜度：候选生成后会话 `version` 变了，主动产出改为重新研判一次，不直接发布。
7. 注意力预算（第 5.7 节）。
8. 去重：`(ticket_id, purpose)` 唯一；同一事项同一用途只发一次。

产出类型：`chat_message`（写进唯一聊天，作为一条猫消息，`turn_id` 为空、`ticket_id` 非空）、`mailbox_letter`（信箱里的一封信）、`push`（第五段）。出口先在同一事务里写产出与 `outbox` 收据，再由 pg-boss 投递副作用；前台在线时通过 `/v1/world/events` 发 `inbox` 提示事件，客户端收到后拉取，内容以 PG 为准。

### 5.5 执行者

- 一件托付一次 `run`；执行者在 worker 里跑，用模型单步函数（当前对应 `runModelStep`），预算见第 5.2 节。
- 每一步结束把该步的模型消息与工具观察写入 `run_steps`；进程中断后，新 worker 从最后一个完整步骤续跑，并在提示里加一句恢复说明：“先核对已有观察，不重复外部动作”。有副作用的工具以 `call_id` 为幂等键。
- 执行者**不能直接开口**，只能调用 `report`：

| 报告 | 含义 | 用户看到 |
|---|---|---|
| `progress` | 内部进展，不外发 | “我在想” |
| `waiting` | 需要用户回答一个具体问题（附 `question`） | 团子在聊天里问一句；用户回答后直达该事项继续 |
| `ready` | 结果可用（附 `result`，≤ 600 字） | 信箱里一封信 + 聊天里一句 |
| `blocked` / `failed` | 办不成（附真实原因） | 团子如实说一句，不硬凑 |
| `dropped` | 发现不需要做 | 不打扰，事项安静结束 |

- 工具白名单（评审点 1 选 A 时）：`get_time`、`get_weather`、`recall_memories`（复用 `memory/recall.ts`，同一套许可过滤）、`read_permitted_diary`（只读 `cat_allowed` 的日记）、`report`。不给移动小猫、写记忆、发消息的工具。
- 模型供应商的 408/429/5xx 与网络错误重试 3 次、退避递增；其他错误报 `failed`。

### 5.6 主动规则与档位

规则是产品方写的文本加开关，存版本表；每次决定记录当时的规则版本。

| 规则 | 授权 | 初始档位 | 依据 |
|---|---|---|---|
| `followup_due` 约定到期 | explicit（用户亲口约的） | 不需要档位，始终生效 | 产品需求“用户定时续聊”已确认 |
| `errand_result` 托付结果 | explicit | 不需要档位 | 用户亲口托付 |
| `daily_diary` 每日猫日记 | 产品规则 | `auto` | 2026-09-12 决策“团子每天自己写一条日记” |
| `ask_outcome` 用户提过近期重要的事，事后问一句结果 | inferred | `observe` | 新增，先观察 |
| `quiet_return` 久未来访后的低优先招呼 | inferred | `off` | 产品需求列为“P1 后再评估” |

用户侧另有许可（09-27 方案第三段“关系许可”）：“允许团子主动找我”总开关默认**关**；关闭时只发 explicit 产出与每日日记（日记只进信箱，不推送）。

### 5.7 注意力预算（提案默认值，评审可改）

- 安静时段：用户本地 22:00–09:00；到期落在安静时段内的约定顺延到 09:00；同一时刻多件到期合并成一条。
- 错过：约定到期后超过 24 小时用户仍未打开，不再补发提问，改为信箱里一封短信，不推送。
- 推断类开口：每个自然日至多 1 次；用户对同类开口说“不要再提”或关闭许可后立即停止。
- 推送（第五段）：每个自然日至多 2 条，只为 `followup_due`、`errand_result`（`ready`/`waiting`）发送；日记不推送。
- 托付：每猫同时最多 2 件在办，每日新建至多 5 件；超出时团子当场说“这件我先记着，前面那件办完再来”，并以 `queued` 状态排队。

## 6. 数据与接口

### 6.1 新增表（增量迁移，不改现有表的语义）

| 表 | 主要字段 | 约束 |
|---|---|---|
| `users.time_zone` | IANA 时区名，默认 `Asia/Shanghai` | 客户端每次启动上报；变化时重算未来事项的本地展示，`due_at`（UTC）不变 |
| `triggers` | `cat_id, source, idempotency_key, payload, received_at` | `(cat_id, source, idempotency_key)` 唯一 |
| `decisions` | `trigger_id, outcome, reasons jsonb, rule_version, ticket_id?` | 只增不改 |
| `tickets` | `cat_id, kind(followup/errand/diary), goal, mandate jsonb, status(open/ended), stage, due_at?, time_zone?, source_message_id?, ended_reason?` | `kind=diary` 时 `(cat_id, local_day)` 唯一 |
| `ticket_inputs` | `ticket_id, message_id?, text?, read_at?` | 用户追加的话直达事项 |
| `runs` | `ticket_id, status(pending/running/ended), attempt, lease_until, report jsonb` | 同一事项同时只有一个 running |
| `run_steps` | `run_id, step, messages jsonb, usage, finished_at` | `(run_id, step)` 唯一 |
| `outbox` | `cat_id, ticket_id?, purpose, kind(chat_message/mailbox_letter/push), status(pending/sent/dropped), dropped_reason?` | `(ticket_id, purpose)` 唯一 |
| `mailbox_letters` | `cat_id, ticket_id?, text, created_at, read_at?` | 信箱里的信，与日记分开存 |
| `proactive_rules` | `rule_id, version, text, mode(off/observe/auto)` | 版本只增 |
| `messages.ticket_id` | 可空 | 主动发出的猫消息指向事项 |

### 6.2 接口

| 接口 | 用途 |
|---|---|
| `PUT /v1/me/time-zone` | 上报 IANA 时区 |
| `GET /v1/tickets?status=open` | “我的”里的约好的事 / 托团子的事，含阶段与下次时间 |
| `PATCH /v1/tickets/:id` | 改时间（约定）或补一句话（托付），后者写 `ticket_inputs` |
| `POST /v1/tickets/:id/cancel` | 取消，立即撤回授权；已排队未发布的产出在出口被丢弃 |
| `GET /v1/mailbox?after=<seq>` | 信箱里的信，分页；`POST /v1/mailbox/:id/read` 标记已读 |
| `/v1/world/events` 新事件 `inbox` | 前台提示有新消息或新信，客户端收到后拉取 |
| `POST /v1/devices`（第五段） | 登记 APNs 设备令牌 |

`GET /v1/messages` 的猫消息增加 `ticket_id` 字段；没有该字段的旧客户端照常显示。

### 6.3 聊天新增工具

| 工具 | 作用 | 回执 |
|---|---|---|
| `schedule_followup` | `{ when: 本地时间 ISO, about: ≤ 60 字 }`，模糊时间（“改天”）不调用，先问清 | 成功返回 `ticket_id` 与规范化后的本地时间；失败给原因 |
| `start_errand` | `{ goal: ≤ 60 字 }` | 成功返回 `ticket_id`；超出预算返回 `queued` |
| `update_ticket` / `cancel_ticket` | 改时间、补一句、取消 | 成功凭证 |
| `list_tickets` | 读未结束事项 | 列表 |

“只有凭证成功才说约好了”写进人设；`persona.ts:82` 改为“只承诺已保存成功的约定与托付；没有凭证不说‘到时候找你’；不编造离线共同经历”。

## 7. 分段（每段单独可合并、合并后系统可用）

### 第一段：底座（用户无感）

1. 引入 `pg-boss`（12.x），替换 BullMQ 的三类投递与清扫；`async_jobs` 仍是权威待办表，pg-boss 只负责投递；Redis 只剩聊天逐字流与断线续传。
2. 抽出 `gate.ts`（硬门）与 `publisher.ts`（发布复核），`turns/run.ts` 与 `worker/diary.ts` 改为调用它们，行为不变。
3. `users.time_zone` 与 `PUT /v1/me/time-zone`；四处 `Asia/Shanghai` 改为读用户时区，缺省仍为 `Asia/Shanghai`。

验收：现有后端回归全部通过；`pnpm smoke`；连续聊天 11 种贯穿链路与四类恢复（[验收报告](../../outputs/chat-continuity-review/验收报告.md)）不退化；停掉 Redis 时记忆提取、边界、日记读取待办仍能在 Redis 恢复后完成；改时区后聊天里“现在”与院子时段按新时区显示。

### 第二段：约好的事

1. `triggers`、`decisions`、`tickets`、`ticket_inputs`、`outbox`、`mailbox_letters`、`proactive_rules` 迁移。
2. 聊天工具 `schedule_followup / update_ticket / cancel_ticket / list_tickets`；人设改写。
3. 时钟来源；`followup_due` 经事件 Router 生成那句提问（Router 只决定措辞与是否合并，不决定是否发送——explicit 事项到期必发，除非被取消或撞上硬门）。
4. 出口写聊天消息与信箱旗子；`/v1/world/events` 发 `inbox`。
5. iOS：聊天中显示约定确认；“我的”里加“约好的事”列表（改时间、取消）；信箱旗子对新信生效。动界面前按 `maomao-ui` 检查表核对。

验收（隔离 PG、mock 模型、模拟器）：同一约定只问一次；到期前取消后不问；到期前把原话设为不再使用后不问；到期落在安静时段顺延；改时区后按新时区到期；到期瞬间重启 worker 不重复、不漏发；同一时刻三件到期合并为一条；用户在约定线程里说“改成后天”直达该事项；模型故障时提问用固定模板兜底，不沉默漏掉 explicit 约定；真实模型抽样核对措辞。

### 第三段：托团子的事

1. `runs`、`run_steps`；执行者、`report`、恢复说明、工具白名单。
2. 聊天工具 `start_errand`；预算与排队。
3. `waiting` 的提问回到聊天，用户回答直达事项；`ready` 写信与一句话；`blocked / failed` 如实说明；`dropped` 安静结束。
4. iOS：“我的”里同一列表显示托付及阶段（我在想 / 在等你 / 好了 / 没办成）；信箱里能读信。

验收：执行到第 N 步时杀掉 worker，新进程从第 N 步续跑且不重复工具副作用；执行中用户取消，结果不发布；执行中用户补一句，下一步读到；执行中关掉记忆，依赖记忆的结果不发布；`waiting` 后用户 24 小时不答，事项转为安静等待、不再追问；超预算排队提示正确；真实模型对 10 条固定托付人工核对“有帮助、团子语气、办不成如实说”。

### 第四段：团子自己的日子

1. `daily_diary` 规则：跨日事件 → 事件 Router 判断当天有无可写的真实事件 → 执行者写一篇 → 出口写入日记（与用户“今日小记”分开），每猫每地日至多一篇。
2. 素材只来自当天已确认的世界回执、对话摘要中用户允许使用的部分、天气；没有就写不涉及用户的猫日常。

验收：关 App 跨三天，每天恰好一篇；重复投递不出第二篇；当天“不要再提”的话题不出现；不出现未发生的共同经历（固定反例集）；时区变化当天不重复、不缺。

### 第五段：离线投递与正式身份

1. 测试环境部署（一个镜像跑 API 与 worker，托管 PG 与 Redis，HTTPS，环境隔离，密钥配置，回退）。
2. APNs（.p8 令牌认证）与 `POST /v1/devices`；推送文案用团子语气，点开回到聊天对应位置或信箱。
3. Sign in with Apple，替换开发者 token。

验收：App 关闭时约定到期收到推送且只一条；点推送进入正确位置；推送前事项被取消不推；每日推送上限生效；令牌失效清理；部署回退演练一次。部署地点见评审点 2。

### 第六段：推断的主动开口

1. `ask_outcome` 以 `observe` 上线：事件 Router 对符合条件的聊天事件做研判，只记录“本来会问”。
2. 内测期按聚合指标（本来会问的次数、其中用户随后自己提起的比例）决定是否切 `auto`；切换写决策记录。
3. 用户侧“允许团子主动找我”开关与“不要再提”同时生效。

验收：`observe` 期无任何外发；切 `auto` 后每日至多 1 次；开关关闭立即停止；规则版本变化时，按旧版本评估中的事件丢弃重评。

## 8. 否决的方案

| 方案 | 原因 |
|---|---|
| 把 DeepSeek Harness 当服务端宿主，直接改原型 | 0.2.x alpha/rc；单操作者、满权限、单 SQLite；面向编码与 GitHub/飞书 |
| Temporal / Restate / Cloudflare Durable Objects | 多一个服务或平台锁定；“定时即来源”后不需要工作流引擎 |
| DBOS 持久化工作流 | 可作为第三段执行者变长后的备选；现在引入会让“挂起”有两种写法 |
| 每个用户常驻 Router 会话 | 成本与上下文膨胀 |
| 用户消息先过 Router 再回话 | 首字前多一次模型调用 |
| 把聊天轮次挪进 worker | 首字前多一次队列轮询，换来的只是崩溃后自动重答；现有“判失败 + 客户端重试”已够 |
| 最小方案：一张约定表 + worker 到点伪造一个聊天轮次 | 能更快做出“约好的事”，但成为第四套执行路径，复核再抄一遍，第三段时要返工 |

## 9. 迁移与回退

- 全部为增量迁移；新代码启动前先停旧 API 与 worker，执行 `pnpm db:migrate`。
- 回退：停掉时钟来源与事件 Router 的 worker 处理器，即不再产生任何主动产出；已写入的事项保留，`GET /v1/tickets` 仍可读、可取消。聊天工具通过移除工具注册即可下线，不影响普通聊天。
- 第一段的 BullMQ → pg-boss 可单独回退：`async_jobs` 未变，回到旧投递代码即可，由恢复扫描补投。
- 撤回与阻断在任何回退下都不放开：出口复核是唯一发布路径，回退只会让团子少说，不会多说。

## 11. 风险与最脆弱的假设

- **最脆弱的假设：用户不在时能收到。**第五段之前，所有产出只能在本机服务运行时生成、用户下次打开 App 时看到，价值减半。设计上产出先落聊天和信箱，推送后接，推迟部署不返工。
- **便宜模型的研判质量。**事件 Router 判错时最坏结果是“该问没问”或“记了一条本来会问”；explicit 事项不依赖它的判断，inferred 开口有代码复核与 `observe` 档兜底。
- **执行者的结果质量。**托付质量取决于模型；`blocked / failed` 必须如实，固定样本人工核对后才对外宣传这项能力。
- **成本。**每件托付最多 8,000 输出 token 加思考；每日新建上限 5 件；`model_calls` 按 `purpose` 记账，第五段上线前补每账号日预算的硬上限。

## 12. 评审点（需要用户拍板）

1. **办事范围。**A（推荐）：只做团子相关——约好的事、托付里的想法整理与建议、日记、院子；B：加联网检索与外部文档，需要隔离执行环境、注入防护与更高成本，另立方案。
2. **部署地点与时间。**国内用户需在国内云部署，面向公众的生成式 AI 服务上线前按当时现行规定办理备案或登记；海外可用海外托管。第五段可前移到第二段之后。
3. **执行者模型。**先用 `deepseek-flash` 开思考（推荐，零新增配置）；若托付质量不够，再评估更强的模型。
4. **注意力预算默认值。**第 5.7 节的安静时段、每日上限、错过规则。
5. **“允许团子主动找我”默认关闭。**关闭时仍发 explicit 产出与每日日记（只进信箱）。
